# ADR: Справочник номенклатуры 1С:УПП на Django

Статус: принято (по итогам сессии grill-me, 2026-09-04)
Контекст проекта: см. [handoff-spravochnik-nomenklatury.md](handoff-spravochnik-nomenklatury.md)

Внутренний read-only справочник номенклатуры для конструкторов ООО «ПРОСТОР-Л»
(ледовые арены). Проблема: конструкторы не работают в 1С:УПП и плодят дубли
номенклатуры. Решение — удобный поиск + замыкание цикла через заявки на новые
позиции, которые заводит один человек (Владимир) по единым правилам.

Единственная аудитория — конструкторы. Склад и ОМТС работают в 1С напрямую.

**Валидация на живых данных (2026-09-04).** Схема выгрузки (ADR-003, ADR-005,
ADR-008) проверена запросами в консоли запросов на копии `UPP_PL_VLAD` —
подробности в ADR-014.

---

## Свод для разработки

### Границы MVP

- В первом релизе: поиск, просмотр номенклатуры, заявки на новые позиции, показ
  залежавшихся остатков.
- Только головная номенклатура. Характеристики номенклатуры 1С не используются.
- Запись из Django в 1С отсутствует. Синхронизация односторонняя 1С → Django.

### Отложено (не в MVP)

- Email-уведомления по заявкам.
- Связь заявки с итоговой позицией (`resulting_nomenclature`).
- Вложения файлов к заявкам.
- Дата последнего движения / оценка неликвида по обороту.
- MPTT/treebeard для дерева папок.
- JSON-поле `extra` на номенклатуре под редкие реквизиты.

## ADR-001. Стек: Django + PostgreSQL

**Решение.** Django + PostgreSQL. Postgres обязателен ради полнотекстового поиска
с русской морфологией и `pg_trgm` (триграммный нечёткий поиск).

**Причина.** Ключевая функция — ловить похоже/иначе записанные названия
(болт/винт, `М10`/`M10`, оцинк/оцинкованный). MySQL нативного триграммного
поиска не даёт.

**Следствия.** Нужны расширения `pg_trgm` (и при необходимости `unaccent`),
GIN-индексы `gin_trgm_ops` по `name` и `article`.

## ADR-002. Масштаб и производительность

**Решение.** Рассчитываем на ~30–40 тыс. позиций номенклатуры, несколько складов.

**Следствия.**

- Обычные индексы + GIN для поиска.
- Агрегаты остатков и признак «залежалось» денормализуются на `Nomenclature`
  (см. ADR-009), не считаются на каждый запрос списка.
- Дерево папок (сотни строк) — рекурсивный запрос Postgres, спец-библиотека не
  нужна.

## ADR-003. Классификация: «Вид номенклатуры» + папки

**Решение.**

- «Вид номенклатуры» (реквизит 1С, плоский список ~22 значений) — базовый уровень
  классификации.
- Папки — **не отдельный справочник в 1С**: это элементы того же
  `Справочник.Номенклатура` с `ЭтоГруппа = Истина`, связь — реквизит `Родитель`.
  Выгружаются как отдельная сущность (`code` / `parent_code` / `name`),
  отфильтрованные по `ЭтоГруппа = Истина`; дерево строится в Django.
- Каждая позиция ссылается и на вид (`ВидНоменклатуры`), и на папку (`Родитель`).

**Причина.** «Вид» — готовая управляемая классификация, удобно вешать порог
отсечки. Но он грубоват («Сырьё и материалы» смешивает крепёж, лист, метраж),
поэтому нужен доступ к папкам для переопределения порога глубже.

## ADR-004. Порог «залежавшихся» остатков

**Решение.**

- Признак «залежалось» = `суммарный доступный остаток ≥ порог`. Без учёта времени
  (дату последнего движения не выгружаем — залежавшихся позиций немного).
- Порог — абсолютное число в базовой ЕИ позиции (`base_unit` из 1С).
- Правила порога — таблица `ThresholdRule` с nullable FK на вид / папку /
  позицию. Приоритет применения: **позиция > папка > вид**.
- Порог и фильтры настраиваются в Django, а не жёстко в выгрузке 1С.

**Причина.** «Много» для крепежа, метража кабеля и листа — разные числа и ЕИ.
Переопределение на папку/позицию разруливает смешанные ЕИ внутри вида.

## ADR-005. Остатки: разрез по складам, учёт резерва

**Решение.**

- 1С выгружает остатки разрезом (позиция, склад): `qty` (физический остаток) и
  `reserved` (в резерве). Отдельный файл, отдельное расписание.
- Доступный остаток = `qty − reserved`, вычисляется в Django.
- Витрина и признак «залежалось» — сумма доступного по видимым складам.
- Карточка позиции — разбивка по складам.
- Видимость складов — флаг `Warehouse.is_visible`, настраивается в Django
  (исключить брак, ответхранение, удалённые склады).

**Причина.** Метка «залежалось» теряет доверие, если большой остаток на самом
деле в резерве или на нерелевантном складе. Держим обе цифры, чтобы показать
конструктору «10 000 на складе, 9 500 в резерве → свободно 500».

## ADR-006. Поиск

**Решение.**

- Основной — полнотекстовый поиск Postgres (`to_tsvector` с русским словарём) по
  `name` + `article`.
- Дополнительный — `pg_trgm` (`similarity`, GIN `gin_trgm_ops`) для опечаток и
  иных написаний.
- Фасеты-фильтры: вид, папка, «только залежавшиеся», «есть на складе».

**Причина.** FTS решает «найти по словам» с морфологией, триграммы — «поймать
иначе записанное». Вместе закрывают обе задачи. Без фасетов 40 тыс. позиций не
сузить.

---

## ADR-007. Антидубль в форме заявки

**Решение.** При создании заявки конструктор вводит предполагаемое название → на
лету показываются топ-10 похожих существующих позиций (триграммы) → перед
отправкой он обязан по каждой отметить «да, это оно» либо «просмотрел, не
подходит». Отмеченные «не подходит» позиции сохраняются в заявку.

**Причина.** Пассивная подсказка игнорируется так же, как игнорируется поиск в
1С. Обязательный шаг стоит ~15 секунд и отсекает большую часть ложных заявок;
Владимиру видно, что человек реально проверил.

## ADR-008. Модель данных

```
NomenclatureKind
  code_1c (unique), name

Folder
  code_1c (unique), name, parent (self-FK, nullable)

Nomenclature
  code_1c (unique, ключ синхронизации)
  name, article, base_unit
  kind (FK NomenclatureKind), folder (FK Folder)
  is_active (bool; пометка удаления в 1С)
  updated_at
  # денормализовано при импорте остатков:
  total_available (Decimal), is_stale (bool)

Warehouse
  code_1c (unique), name, is_visible (bool)

StockBalance
  nomenclature (FK), warehouse (FK)
  qty (Decimal), reserved (Decimal), updated_at
  unique_together (nomenclature, warehouse)

ThresholdRule
  kind (FK, nullable), folder (FK, nullable), nomenclature (FK, nullable)
  threshold (Decimal)
  # ровно одно из трёх FK заполнено; приоритет nomenclature > folder > kind

Request
  author (FK User), created_at
  description (text)
  similar_to (FK Nomenclature, nullable)
  reviewed_not_matching (M2M Nomenclature)   # «просмотрел, не подходит»
  guess_kind, guess_unit, gost_or_article, analog_url  # структурные поля
  status (new / approved / entered / closed / rejected)
  resolution_comment, resolved_by (FK User, nullable), resolved_at

ImportLog
  started_at, finished_at
  kind (reference / stock)
  source_file, file_hash
  status (ok / error / partial)
  rows_total, rows_created, rows_updated, rows_failed
  error_text

ImportRowError
  import_log (FK), row_code, reason
```

**Причина ключевых выборов.**

- FK-справочники (не текстовые поля) — целостность и удобная админка для
  простановки порогов.
- Денормализация `total_available` / `is_stale` — производительность списка и
  сортировки по «залежалось».
- `Warehouse` отдельной моделью — ради `is_visible`.
- `ImportRowError` построчно — иначе «частично: 47 не легло» без возможности
  починить.

## ADR-009. Синхронизация 1С → Django

**Топология.**

- База 1С — клиент-серверная (сервер 1С:Предприятия на localhost). Штатный сервер
  регламентных заданий выполняет выгрузку сам, без RDP-сессии и внешнего
  планировщика.
- Обработка-выгрузка разрабатывается на копии `UPP_PL_VLAD`; боевой регламент —
  в рабочей базе.
- Сервер 1С и сервер Django — одна машина (Windows). Файл передаётся через
  локальную папку.

**Формат.** JSON, UTF-8.

- Файл справочников: номенклатура + виды + папки (полный снимок).
- Файл остатков: разрез (позиция, склад), `qty` + `reserved`.

**Надёжность.**

- 1С пишет во временное имя (`*.tmp`) → атомарный `rename` в финальное.
- Django не импортирует файл с уже виденным хэшем (`ImportLog.file_hash`).
- Импорт — идемпотентный `update_or_create` по `code_1c`.
- Порядок импорта справочников: виды → папки → номенклатура → остатки.
- Guard: если позиций в выгрузке резко меньше, чем в прошлый успешный импорт,
  импорт останавливается с ошибкой, изменения не применяются.

**Удаление.** 1С выгружает все позиции, помеченные на удаление — с
`is_active=false`. Django прячет их из поиска; карточка доступна по прямой ссылке
с плашкой «не актуально». Физического удаления в Django нет (ломает `similar_to`
и историю заявок).

**Расписание.**

- Справочники — раз в сутки ночью (~03:00).
- Остатки — каждые 3–4 часа в рабочее время.
- Django-задача читает файл через 10–15 мин после окна выгрузки 1С.

## ADR-010. Запуск импорта

**Решение.** Windows Task Scheduler → `python manage.py import_1c --kind=…`.
Синхронная management-команда с lock-файлом (два прогона не пересекаются).
Без Celery / Redis / django-q.

**Причина.** Импорт раз в несколько часов, без параллельности и веб-триггеров.
Брокер очередей — лишняя инфраструктура под несуществующую нагрузку.

---

## ADR-011. Аутентификация и роли

**Решение.**

- Локальные учётки Django. Пользователей заводит Владимир (десятки конструкторов).
- Доменную SSO/LDAP в MVP не делаем.
- Роли: конструктор (поиск, просмотр, свои заявки, чужие заявки — просмотр) и
  Владимир (админка, одобрение заявок, простановка порогов, видимость складов).

**Следствие для деплоя.** Пароли Django идут по сети → нужен HTTPS (ADR-013).

---

## ADR-012. Процесс заявок

**Решение.**

- Уведомления в MVP — только на сайте: раздел «мои заявки» со статусами;
  счётчик новых заявок у Владимира. Email — позже, поверх, когда появится
  SMTP-релей.
- Все конструкторы видят все заявки (защита от параллельных дублей между
  людьми). Автор не скрыт.
- Статусы: `new` → `approved` → `entered` → `closed`; ветка `rejected`.
  «entered» («заведена в 1С») Владимир ставит вручную после ввода позиции.
  Промежуточный статус закрывает поток вопросов «ты одобрил, где позиция».
- Авто-привязку заявки к итоговому `code_1c` не делаем (ручное сопоставление).
- Вложений файлов нет; только структурные поля + URL на аналог.

## ADR-013. Веб-стек и инфраструктура (Windows)

**Решение.**

- WSGI-сервер — Waitress, запускается как служба Windows через NSSM.
- Впереди — Nginx для Windows (статика, буферизация, терминация TLS).
- Postgres — штатный инсталлятор под Windows.
- Gunicorn / systemd / WSL не используются (WSL добавляет неподдерживаемый слой
  на сервере с боевым 1С). Переезд на отдельную Linux-машину позже — без
  изменения кода.

**DNS.** A-запись в AD DNS: `spravochnik.<домен>` → IP сервера.

**HTTPS.** Сертификат от внутреннего AD Certificate Services на
`spravochnik.<домен>`, доверенный на доменных машинах автоматически; Nginx
терминирует TLS. Если AD CS не развёрнут — на MVP допустим HTTP с требованием не
переиспользовать важные пароли, но HTTPS в ближайший бэклог (не «на горизонт»).

**Бэкап.** `pg_dump` ежедневно через Task Scheduler на тот же сетевой ресурс, что
и бэкап 1С; хранить ~30 копий. Справочник восстановим ресинхронизацией, но
заявки и пороги существуют только в Django.

## ADR-014. Валидация выгрузки на живых данных

**Статус.** Схема ADR-003/ADR-005/ADR-008 проверена запросами в консоли
запросов на копии `UPP_PL_VLAD` (2026-09-04). Подтверждено реальными данными,
без противоречий с ранее принятыми решениями.

**Номенклатура.** Существующий рабочий запрос (`выбор номенклатуры.sel`) даёт
все нужные поля напрямую:

```sql
ВЫБРАТЬ
    Ном.Код КАК Код,
    Ном.Артикул КАК Обозначение,
    Ном.Наименование КАК Наименование,
    Ном.НаименованиеПолное КАК НаименованиеПолное,
    Ном.БазоваяЕдиницаИзмерения КАК БазоваяЕдиница,
    Ном.ЕдиницаХраненияОстатков КАК ЕдиницаХранения,
    Ном.ВидНоменклатуры КАК ВидНоменклатуры,
    Ном.НоменклатурнаяГруппа КАК НоменклатурнаяГруппа,
    Ном.СтатьяЗатрат КАК СтатьяЗатрат,
    Ном.Родитель КАК Группа,
    Ном.Услуга КАК Услуга,
    Ном.Комментарий КАК Комментарий
ИЗ
    Справочник.Номенклатура КАК Ном
ГДЕ
    НЕ Ном.ЭтоГруппа
    И НЕ Ном.ПометкаУдаления
УПОРЯДОЧИТЬ ПО
    Ном.Код
```

Подтверждено: `Ном.БазоваяЕдиницаИзмерения` и `Ном.ЕдиницаХраненияОстатков`
всегда совпадают в этой базе — используем одно поле `base_unit` без различения
(упрощение относительно первоначальной формулировки ADR-005/ADR-008).
`НЕ Ном.ПометкаУдаления` — готовый фильтр для `is_active` (инвертировать при
выгрузке). Папки — см. правку ADR-003 (реквизит `Родитель` того же
справочника, не отдельная сущность 1С).

**Остатки и резерв.** Регистр остатков — `ТоварыНаСкладах` (как и
предполагалось). Регистр резерва в этой конфигурации называется
**`ТоварыВРезервеНаСкладах`** (не `ТоварыКОтгрузке`, как было предположено в
ADR-005 — название регистра варьируется между конфигурациями УПП). Проверочный
запрос:

```sql
ВЫБРАТЬ
    Свод.Номенклатура.Код КАК КодНоменклатуры,
    Свод.Номенклатура.Наименование КАК Номенклатура,
    Свод.Склад.Код КАК КодСклада,
    Свод.Склад.Наименование КАК Склад,
    Свод.Остаток КАК Остаток,
    Свод.ВРезерве КАК ВРезерве
ИЗ
    (ВЫБРАТЬ
        ЕСТЬNULL(Остатки.Номенклатура, Резерв.Номенклатура) КАК Номенклатура,
        ЕСТЬNULL(Остатки.Склад, Резерв.Склад) КАК Склад,
        ЕСТЬNULL(Остатки.Количество, 0) КАК Остаток,
        ЕСТЬNULL(Резерв.Количество, 0) КАК ВРезерве
    ИЗ
        (ВЫБРАТЬ
            Т.Номенклатура КАК Номенклатура,
            Т.Склад КАК Склад,
            СУММА(Т.КоличествоОстаток) КАК Количество
        ИЗ
            РегистрНакопления.ТоварыНаСкладах.Остатки(, Номенклатура.ЭтоГруппа = ЛОЖЬ) КАК Т
        СГРУППИРОВАТЬ ПО
            Т.Номенклатура, Т.Склад) КАК Остатки

        ПОЛНОЕ СОЕДИНЕНИЕ

        (ВЫБРАТЬ
            Р.Номенклатура КАК Номенклатура,
            Р.Склад КАК Склад,
            СУММА(Р.КоличествоОстаток) КАК Количество
        ИЗ
            РегистрНакопления.ТоварыВРезервеНаСкладах.Остатки(, Номенклатура.ЭтоГруппа = ЛОЖЬ) КАК Р
        СГРУППИРОВАТЬ ПО
            Р.Номенклатура, Р.Склад) КАК Резерв

        ПО Остатки.Номенклатура = Резерв.Номенклатура
            И Остатки.Склад = Резерв.Склад) КАК Свод

УПОРЯДОЧИТЬ ПО
    КодНоменклатуры,
    КодСклада
```

Результат подтвердил модель `StockBalance` (ADR-005/ADR-008) построчно:
реальные склады — `ПРОСТОР-Л МАТЕРИАЛЫ`, `Производство`, `Склад
Богослово(стройка)`, `Салехард`. На складе «Производство» остаток и резерв
всегда совпадают (материалы, выданные в работу, полностью зарезервированы под
заказ) — доступный остаток там корректно обнуляется формулой `qty − reserved`
без ручных исключений. «Салехард» и «Богослово(стройка)» — реальные кандидаты
на `Warehouse.is_visible = false` как физически недоступные конструктору
площадки.

**Вывод.** Оба запроса — прямая основа для 1С-обработки выгрузки (шаг 3 ниже);
достаточно обернуть результат в сериализацию JSON и запись во временный файл
с атомарным `rename` (ADR-009).

## Рекомендуемый порядок разработки

1. Модели Django (ADR-008) + миграции, включить `pg_trgm` / FTS-конфиг.
2. Management-команда `import_1c` (ADR-009, ADR-010): парсинг JSON, `update_or_create`,
   `ImportLog` / `ImportRowError`, guard на падение объёма, lock-файл.
3. Пример обработки-выгрузки в 1С (JSON, `*.tmp` → `rename`) — на копии
   `UPP_PL_VLAD`.
4. Поиск + фасеты (ADR-006), карточка позиции с разбивкой остатков.
5. Заявки (ADR-007, ADR-012): форма с антидублем, список, статусы, админка
   одобрения.

# Деплой справочника номенклатуры (шаг 7 ADR, MVP-объём)

Статус: принято (сессия 2026-09-04)
Контекст: [assets/adr-spravochnik-nomenklatury.md](../../../assets/adr-spravochnik-nomenklatury.md)
(ADR-013 «Веб-стек и инфраструктура (Windows)», раздел «Рекомендуемый
порядок разработки», шаг 7), [assets/handoff-spravochnik-nomenklatury.md](../../../assets/handoff-spravochnik-nomenklatury.md).

## Контекст и ограничения

Целевой продакшен-сервер — отдельная Windows-машина (не машина
разработки), с которой у Владимира на момент написания этой спеки нет
доступа (ни RDP, ни подтверждённой информации об инфраструктуре AD).
Материалы этого шага нельзя проверить вживую на целевой машине —
только на машине разработки (где уже установлен и рабочий PostgreSQL 17,
см. коммит «Исправлен поиск на реальном Postgres»).

Из этого следует:

- Деплой-материалы должны быть самодостаточными и проверяемыми по шагам
  (раннбук с чекпоинтами), а не «одна кнопка — и готово» — иначе первая
  же ошибка на незнакомой машине не будет видна до конца прогона.
- Статус Active Directory (DNS, Certificate Services) в организации не
  подтверждён. Раннбук не может полагаться на AD как на данность —
  описывает оба пути (AD и fallback), не только один.
- Nginx и TLS явно выведены за рамки этого шага (ADR-013 сам помечает
  их как «впереди», не MVP) — по решению в этой сессии. Waitress
  обслуживает HTTP напрямую внутри локальной сети; TLS/Nginx —
  отдельный будущий шаг, когда прояснится статус AD CS.

## Границы MVP этого шага

**В объёме:**

- Установка зависимостей прод-стека (Waitress, WhiteNoise) и правки
  `config/settings.py` под них.
- NSSM-служба Waitress, запускающая Django через WSGI.
- Задачи Task Scheduler: импорт справочников, импорт остатков, бэкап
  `pg_dump`.
- Раннбук, описывающий полный путь установки на чистой машине от
  голого Windows Server до работающего сервиса, включая PostgreSQL,
  firewall, оба варианта DNS/TLS.
- Безопасные значения конфигурации по умолчанию для прод-окружения
  (`SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`) с явной проверкой в раннбуке.

**Не в объёме (отложено явно):**

- Nginx, TLS/HTTPS — следующий шаг, когда будет ясен статус AD CS.
- Реальная установка на целевом сервере — материалы готовятся впрок,
  без возможности проверить на нём самом.
- Мониторинг/алертинг сервиса (кроме того, что даёт сам Task Scheduler
  и Windows Event Log через NSSM).
- HA/масштабирование — вне сферы применения внутреннего инструмента.

## Компоненты

### 1. Правки Django-проекта

`requirements.txt` — добавить `waitress` и `whitenoise` (точные версии
фиксируются на момент реализации).

`config/settings.py`:

- `WhiteNoiseMiddleware` сразу после `SecurityMiddleware` в
  `MIDDLEWARE` — раздача статики без Nginx на MVP.
- `STATIC_ROOT = BASE_DIR / 'staticfiles'`.
- `STORAGES['staticfiles']['BACKEND']` =
  `whitenoise.storage.CompressedManifestStaticFilesStorage` (кэшируемые
  хэшированные имена файлов, gzip).
- Ничего не меняется в логике `DATABASES`/`IMPORT_DIR` — они уже
  читаются из env-переменных (см. ADR-009/README).

### 2. `deploy/env.example`

Шаблон обязательных переменных окружения для прод-запуска, без
секретных значений — только имена и комментарии, что́ в них класть:
`DJANGO_SECRET_KEY`, `DJANGO_DEBUG=False`, `DJANGO_ALLOWED_HOSTS`,
`DJANGO_TIME_ZONE`, `DATABASE_NAME`, `DATABASE_USER`,
`DATABASE_PASSWORD`, `DATABASE_HOST`, `DATABASE_PORT`, `IMPORT_DIR`.

### 3. `deploy/install_service.ps1`

PowerShell-скрипт, идемпотентный (проверяет, существует ли служба,
прежде чем создавать):

- Принимает параметры: путь к venv, порт (по умолчанию 8000), имя
  службы (по умолчанию `spravochnik`).
- `nssm install <service> <venv>\Scripts\waitress-serve.exe
  --host=0.0.0.0 --port=<port> config.wsgi:application`.
- `nssm set <service> AppDirectory <путь к репозиторию>`.
- `nssm set <service> AppEnvironmentExtra` — пробрасывает переменные
  окружения из `.env`-подобного файла (сам скрипт не хранит секреты —
  читает их из файла, путь к которому передаётся параметром, и которого
  нет в репозитории/git).
- `nssm set <service> Start SERVICE_AUTO_START` — автозапуск при
  перезагрузке сервера.
- Настраивает `AppStdout`/`AppStderr` на файлы логов и `AppRotateFiles`
  — иначе лог службы растёт бесконечно.

### 4. `deploy/schedule_tasks.ps1`

Создаёт три задачи через `Register-ScheduledTask` (идемпотентно —
`Unregister-ScheduledTask` перед регистрацией, если уже существует):

- `Spravochnik-ImportReference` — `python manage.py import_1c
  --kind=reference`, ежедневно в 03:00 (ADR-009).
- `Spravochnik-ImportStock` — `python manage.py import_1c --kind=stock`,
  каждые 3 часа в рабочее время (07:00–19:00) — соответствует ADR-009
  («раз в несколько часов в рабочее время»).
- `Spravochnik-Backup` — вызывает `deploy/backup.ps1`, ежедневно ночью
  после импорта справочников.

Обе задачи импорта запускаются под учётной записью, у которой есть
доступ на чтение к сетевой папке выгрузки 1С (ADR-009) — раннбук
явно указывает создать отдельного служебного пользователя, не
привязываться к личной учётке Владимира.

### 5. `deploy/backup.ps1`

- `pg_dump` в файл с меткой времени в имени, на тот же сетевой ресурс,
  что и бэкап 1С (ADR-013).
- Прунинг: удаляет файлы бэкапа старше N (по умолчанию 30, параметр
  скрипта) — соответствует ADR-013 «хранить ~30 копий».
- Пишет свой лог с результатом (успех/ошибка, размер файла) — если
  `pg_dump` тихо перестанет работать, это должно быть видно постфактум,
  не только в момент восстановления.

### 6. `deploy/RUNBOOK.md`

Пронумерованные разделы, каждый шаг — команда(ы) + «как проверить, что
сработало». Разделы:

1. Подготовка Windows Server (учётная запись службы, firewall).
2. PostgreSQL: установка (winget — уже проверено рабочим на машине
   разработки), создание БД/роли, `pg_trgm`/`unaccent`.
3. Клонирование репозитория, venv, `pip install -r requirements.txt`.
4. `.env`-файл на сервере (не в git) по `deploy/env.example`,
   генерация `SECRET_KEY`.
5. `manage.py migrate`, `manage.py collectstatic`,
   `manage.py createsuperuser`.
6. `deploy/install_service.ps1` — запуск и проверка (curl/браузер на
   `http://localhost:8000/`).
7. `deploy/schedule_tasks.ps1` — проверка через `Get-ScheduledTask` +
   тестовый ручной запуск `Start-ScheduledTask`.
8. Firewall: открыть входящее правило на порт Waitress для локальной
   сети (`New-NetFirewallRule`), проверка с другого компьютера в сети.
9. DNS — два варианта чек-листом:
   - Если есть AD с DNS: A-запись `spravochnik.<домен>` → IP сервера.
   - Если нет/не уверены: `dnsmasq` на роутере или статическая запись,
     как обсуждалось в handoff — с пометкой, что это временное решение
     до прояснения статуса AD.
10. TLS — явно помечено «не в этом шаге»: пока `http://`, план на
    будущее (AD CS сертификат + Nginx как терминатор TLS) описан одним
    абзацем со ссылкой на ADR-013, без конкретных команд (нечего
    выполнять, пока не подтверждён AD CS).
11. Проверочный чек-лист «деплой считается успешным, если»: сервис
    в `Get-Service` в состоянии Running, страница поиска открывается по
    IP/hostname, `Get-ScheduledTask` показывает все три задачи, ручной
    прогон `Start-ScheduledTask -Name Spravochnik-Backup` создаёт файл
    дампа.

## Тестирование этого шага

Поскольку у выполняющего эту работу агента нет доступа к целевому
серверу, «тестирование» здесь означает:

- Скрипты пишутся так, чтобы их можно было прочитать и понять, что они
  сделают, без запуска (явные параметры, явные пути, комментарии) —
  ревьюер (или Владимир) должен суметь провалидировать логику чтением.
- Где возможно проверить локально без Windows-специфики (например,
  что `config/settings.py` с добавленным `WhiteNoiseMiddleware` не
  ломает существующие тесты, что `collectstatic` отрабатывает без
  ошибок на машине разработки) — проверяется реально, командой, с
  показанным выводом.
- PowerShell-синтаксис скриптов проверяется хотя бы через
  `powershell -NoProfile -Command "$null = Get-Content <script> |
  Out-Null; [scriptblock]::Create((Get-Content <script> -Raw))"` или
  аналогичный parse-only прогон (доступен на машине разработки — она
  тоже Windows) — ловит синтаксические ошибки до попадания на сервер,
  не логические.
- Раннбук явно, в шаге 11, задаёт критерии «успешно» для Владимира,
  когда он будет прогонять его на реальном сервере.

## Открытые вопросы (на будущее, не блокируют этот шаг)

- Статус AD (DNS/CS) — уточнить перед выполнением разделов 9–10
  раннбука на реальном сервере.
- Учётная запись для Task Scheduler — под какой конкретно учёткой
  заводить задачи, решает Владимир на месте (зависит от прав на
  сетевую папку 1С).
- Реальный прогон раннбука на целевой машине и правки по его
  результатам — отдельная будущая сессия, когда появится доступ.
